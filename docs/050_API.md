## 1. Purpose

This document defines the API contract standards for Project Atlas internal and external HTTP APIs.

APIs are security and compatibility boundaries. Their schemas, authorization behavior, errors, asynchronous operations, events, and lifecycle must be defined before implementation and verified continuously.

## 2. Scope

### In Scope

- API styles, resource design, schemas, versioning, errors, pagination, filtering, and concurrency
- Authentication, authorization, policy, approval, audit, and data-boundary behavior
- Long-running operations, chat streaming, event subscriptions, and idempotency
- Documentation, compatibility, deprecation, observability, and testing
- Initial API domains and MVP boundaries

### Out of Scope

- Backend module implementation covered by ATLAS-051
- UI behavior covered by ATLAS-052
- Vendor MCP wire protocols governed by ATLAS-020
- Database schemas covered by ATLAS-053
- Public SDK language selection

## 3. Objectives

- Provide explicit, machine-readable, stable contracts
- Enforce the same identity, scope, policy, and audit rules across UI and API clients
- Make long-running and partial work trackable
- Prevent ambiguous success, hidden retries, and accidental duplicate actions
- Support additive evolution and predictable deprecation
- Preserve correlation, evidence, version, freshness, and classification
- Work in connected and restricted-network deployments

## 4. API Styles

| Style | Use |
| --- | --- |
| REST over HTTPS | Primary resource, command, query, administration, and integration API |
| Server-Sent Events | One-way chat token or event progress streaming to browser clients |
| Versioned platform events | Asynchronous service and integration notifications under ATLAS-016 |
| Internal RPC | Only where an ADR proves need; still schema-first and authenticated |
| WebSocket | Not default; requires an ADR for bidirectional real-time use |

GraphQL is not an MVP default. Infrastructure graph queries use bounded typed REST resources rather than arbitrary traversal exposure.

## 5. Contract-First Standard

- OpenAPI 3.1 is mandatory for supported REST APIs.
- JSON Schema defines request, response, event, configuration, and artifact payloads.
- The contract is reviewed before or with implementation.
- Generated server/client types may be used, but generated code does not replace runtime validation.
- Examples use synthetic data and include success, denial, validation, conflict, partial, and failure cases.
- CI detects implementation-contract drift and breaking changes.
- Published contracts are versioned release artifacts.

## 6. Resource Design

- Resources use stable plural nouns and opaque identifiers.
- HTTP methods retain standard semantics.
- Commands that do not map cleanly to CRUD use explicit subresources or operation resources.
- Domain resources expose platform-normalized names while preserving vendor evidence where needed.
- Relationships use identifiers or links and do not embed unbounded object graphs.
- Collection responses are bounded and paginated.
- Deletion defaults to lifecycle transition where retention or audit applies.
- URLs do not contain secrets or sensitive free-form content.

Example patterns:

```text
/api/v1/connectors
/api/v1/connectors/{connector_id}/capabilities
/api/v1/investigations/{investigation_id}
/api/v1/recommendations/{recommendation_id}
/api/v1/operations/{operation_id}
```

## 7. API Domain Catalog

- Authentication sessions and current identity
- Users, groups, roles, assignments, scopes, and access reviews
- Connectors, packages, instances, targets, credentials references, and capabilities
- Inventory, observations, health, topology, graph queries, and service impact
- Knowledge sources, items, ingestion jobs, retrieval evidence, and feedback
- Conversations, investigations, reasoning, RCA, recommendations, and reports
- Workflows, definitions, runs, schedules, and tasks
- Policies, simulations, decisions, and exceptions
- Approval requests and decisions
- Audit search, reports, and governed exports
- Syslog, SIEM, ITSM, model, and notification integrations
- Platform configuration, health, support, backup, and deployment status

## 8. Representation Rules

- JSON is the default representation with UTF-8 encoding.
- Field names use `snake_case` consistently.
- Timestamps use RFC 3339 UTC with explicit offset.
- Durations use ISO 8601 or a documented integer unit; APIs do not mix implicit units.
- Enumerations use stable lowercase identifiers.
- Identifiers are strings and clients do not infer meaning from their format.
- Decimal and high-precision values avoid unsafe floating-point representation where material.
- Optional, absent, empty, unknown, and redacted remain distinguishable.
- Sensitive fields are omitted or represented by safe references, never dummy secret values.

## 9. Standard Resource Metadata

Resources include, as applicable:

- `id`, `resource_type`, and `version`
- `created_at`, `created_by`, `updated_at`, and `updated_by`
- `state` and lifecycle timestamps
- `organization_id`, `environment_id`, and declared scope references
- `classification`
- `etag` or revision for concurrency
- `links` for governed related resources
- `warnings`, freshness, and partial-data metadata

Responses do not expose fields the caller cannot access merely as `null`.

## 10. Authentication and Session Context

- Every protected request uses ATLAS-030 authentication.
- Browser APIs use secure session handling and CSRF protection.
- Service APIs use audience-bound workload credentials or mutual TLS.
- API tokens are short-lived and scope-limited.
- Authentication context is derived server-side; clients cannot assert role or assurance.
- Acting user and delegated service identities remain distinguishable.
- Logout, revocation, expiry, and step-up requirements apply consistently to streaming and asynchronous requests.

## 11. Authorization and Scope

- Every protected endpoint declares required permissions and resource scope.
- Backend enforcement uses ATLAS-031; UI visibility is not a control.
- Collection queries filter unauthorized resources before pagination and counts.
- Bulk operations authorize every target and fail according to declared atomicity.
- Hidden-resource requests return safe errors without confirming existence.
- Policy, approval, and guardrail checks are separate from RBAC.
- An operation resource does not continue under revoked authority without required re-evaluation.

## 12. Request Context and Headers

Supported headers include:

- `Authorization` or secure session cookie
- `Accept` and `Content-Type`
- `X-Correlation-ID` when provided in accepted format
- `Idempotency-Key` for eligible mutations
- `If-Match` for optimistic concurrency
- `Prefer` for documented asynchronous behavior where supported

Atlas generates canonical request, trace, and correlation identifiers and returns safe correlation metadata. Untrusted header values are validated and not copied blindly into logs.

## 13. Input Validation

- Validate schema, type, enum, format, bounds, length, encoding, and cross-field constraints.
- Reject unknown fields by default for consequential command payloads.
- Normalize identifiers, timezones, units, and target selectors before authorization.
- Validate referenced resources within caller scope.
- Bound list sizes, query complexity, graph depth, file size, archive depth, and output limits.
- Uploaded files follow malware, active-content, and classification controls.
- Validation happens before external connector dispatch.
- AI-generated parameters receive the same or stronger validation as user input.

## 14. Error Contract

Errors use a stable envelope based on problem details:

```json
{
  "type": "https://atlas.example/problems/authorization-denied",
  "title": "Request denied",
  "status": 403,
  "code": "authorization_denied",
  "detail": "The current identity is not authorized for this operation.",
  "correlation_id": "cor_opaque",
  "retryable": false,
  "errors": []
}
```

- `code` is stable and machine-readable.
- `detail` is safe for the caller and does not leak hidden resources or control internals.
- Field errors use JSON Pointer or equivalent paths.
- Retryability and retry timing are explicit where known.
- Partial, timeout, conflict, stale, and unknown outcomes have distinct codes.
- Stack traces and vendor secrets are never returned.

## 15. HTTP Status Semantics

- `200` or `201`: completed successful request
- `202`: accepted asynchronous operation with operation resource
- `204`: successful response with no body where appropriate
- `400`: malformed or invalid request
- `401`: authentication required or invalid
- `403`: authenticated but not authorized or policy permits no detail
- `404`: absent or intentionally concealed resource
- `409`: state, idempotency, or lifecycle conflict
- `412`: optimistic-concurrency precondition failure
- `422`: semantically invalid structured request where used consistently
- `429`: rate or resource limit
- `5xx`: server or dependency failure, never business denial

A timeout or unknown external result must not return ordinary success.

## 16. Pagination, Filtering, and Sorting

- Cursor pagination is the default for changing or large collections.
- Page size has secure defaults and enforced maximums.
- Cursors are opaque, signed or integrity-protected, scoped, and expiring.
- Filters and sort fields are allowlisted and documented.
- Stable tie-break sorting prevents skipped or duplicate records where possible.
- Counts are optional and authorization-safe.
- Search complexity and result windows are bounded.
- Export of a full collection is a separate governed asynchronous operation.

## 17. Optimistic Concurrency

- Mutable governed resources expose revision or ETag.
- Updates use `If-Match` or an explicit expected revision.
- Stale updates return conflict or precondition failure with current safe metadata.
- Last-write-wins is prohibited for policy, role, approval, workflow, connector, and consequential plan state.
- Append-only resources create new versions or events.
- Conflict resolution is domain-specific and audited.

## 18. Idempotency

- Eligible create and command requests accept an `Idempotency-Key`.
- Keys are scoped to subject, endpoint, organization, and time window.
- The server stores request digest, status, operation ID, and bounded response reference.
- Reuse with a different payload returns conflict.
- Retries return the original known result or operation state.
- Unknown connector outcomes trigger reconciliation, not blind replay.
- Keys contain no secrets and have defined retention.

## 19. Long-Running Operations

Requests expected to outlive the HTTP transaction return `202` and an operation resource containing:

- Operation ID, type, owner, scope, state, and progress
- Created, started, updated, deadline, and expiry times
- Input artifact or request version
- Workflow-run and correlation references
- Current step and safe status summary
- Result, partial-result, error, and evidence references
- Cancellation eligibility and reason
- Required human task or approval state

States distinguish queued, running, waiting, succeeded, failed, cancelled, timed out, partial, and unknown.

## 20. Cancellation

- Cancellation is an explicit authenticated command with idempotency.
- The operation declares whether it is cancellable and until which state.
- Cancellation requests do not imply immediate external cessation.
- Final state distinguishes cancelled before dispatch, cancellation requested, stopped, partial, and too late.
- Completed steps and required recovery remain visible.
- Cancellation and outcome are audited.

## 21. Chat and AI Streaming

SSE is the default browser streaming mechanism for:

- Response text fragments
- Structured status transitions
- Evidence and citation additions
- Tool request and result summaries
- Waiting-for-user or waiting-for-approval state
- Final validated artifact reference
- Error, cancellation, and completion

Streams use typed event names, sequence IDs, heartbeat, reconnection cursor, and a terminal event. Draft tokens are not treated as validated final output. Security, redaction, and citation validation can delay or replace draft content.

## 22. Event Subscriptions and Webhooks

- Platform events follow ATLAS-016 schema and compatibility rules.
- Webhooks use registered destinations, TLS, authentication or signatures, replay protection, and bounded retry.
- Subscribers choose allowlisted event classes and scopes.
- Secrets and restricted payloads are excluded or referenced.
- Delivery is at least once unless a stronger contract is declared.
- Consumers deduplicate by event ID.
- Subscription creation, test, disablement, backlog, and replay are audited.

## 23. File Upload and Download

- File endpoints use explicit purpose, type, size, count, and classification limits.
- Uploads are quarantined until scanning and parsing complete.
- Download authorization is evaluated at request time.
- Signed download links are short-lived, audience-bound, and single-purpose where supported.
- Range requests and streaming are bounded.
- Filenames and content disposition are sanitized.
- Export archives include manifest, checksum, classification, and expiry.

## 24. Rate and Resource Limits

- Limits can apply by subject, organization, endpoint, operation type, model, connector, and target.
- Responses expose safe limit and retry information.
- Expensive graph, search, export, AI, and connector requests have explicit quotas and concurrency.
- Security events and required audit are not dropped because a user quota is exhausted.
- Limits prevent one organization or workflow from starving others.
- Administrators can view usage without exposing sensitive request content.

## 25. Versioning

- Major API version appears in the path, such as `/api/v1`.
- Additive compatible changes remain within a major version.
- Breaking field, semantic, enum, error, authorization, or default changes require a new major version or a defined compatibility mechanism.
- Resource and artifact versions are distinct from API versions.
- Event, connector, workflow, policy, and document schemas have independent versions.
- Clients advertise or negotiate only documented capabilities.
- The compatibility matrix is a release artifact.

## 26. Deprecation

- Deprecation identifies replacement, reason, affected clients, announcement, and removal date.
- Deprecated endpoints remain secure and monitored.
- Response headers and API documentation expose deprecation where feasible.
- Removal requires usage evidence, migration guidance, contract tests, and release approval.
- Emergency security retirement follows a shortened governed process and explicit communication.
- Offline customers receive deprecation information in release bundles.

## 27. Security

- HTTPS with approved TLS is mandatory outside isolated local development.
- CORS uses an allowlist and secure defaults.
- Browser endpoints use CSRF, content-security, and secure-cookie controls.
- Request smuggling, path traversal, injection, unsafe deserialization, SSRF, and mass assignment are addressed.
- External URLs and callbacks are allowlisted and resolved through governed integration services.
- Secrets never appear in URLs, schemas, examples, errors, or logs.
- Response headers prevent unsafe caching of sensitive content.
- APIs have threat models appropriate to their data and capability class.

## 28. Audit and Observability

ATLAS-032 governs audit. APIs propagate correlation and record protected activity, denials, policy, approval, connector, export, and administration events.

Operational telemetry includes:

- Request rate, latency, status, and error code
- Authentication, authorization, policy, and validation outcome
- Operation state and age
- Rate-limit, timeout, cancellation, and retry behavior
- Payload size and schema-version distribution
- Deprecated endpoint usage
- Dependency latency and failure

Metrics avoid unbounded user, target, and resource labels.

## 29. Documentation and Developer Experience

- OpenAPI and examples are available in the repository and release bundle.
- Interactive API documentation is disabled or protected in production according to policy.
- Each endpoint documents permission, scope, capability class, audit, idempotency, concurrency, pagination, errors, and rate limits.
- Examples use synthetic identifiers and no credentials.
- Changelog identifies compatible and breaking changes.
- SDK generation, if introduced, pins the contract version and preserves error semantics.

## 30. Testing Requirements

- OpenAPI lint, schema validation, and implementation conformance
- Backward-compatibility and breaking-change detection
- Authentication, RBAC, scope, hidden-resource, policy, and approval behavior
- Input boundaries, unknown fields, injection, file, and malformed payloads
- Error codes and no-secret responses
- Pagination, cursor tampering, sorting, and authorization-safe counts
- Idempotency, retry, concurrency, conflict, and unknown outcomes
- Long-running state, cancellation, partial results, SSE reconnect, and terminal events
- Rate, quota, isolation, timeout, and dependency failure
- Audit and correlation completeness

## 31. MVP Scope

### Included

- OpenAPI 3.1 contract-first REST API under `/api/v1`
- Authentication context, scoped authorization, standard errors, correlation, and audit
- Cursor pagination and optimistic concurrency
- Idempotency for eligible mutations
- Operation resources for long-running work
- SSE for chat and analysis progress
- Initial APIs for current identity, connectors, inventory, knowledge, chat, investigations, recommendations, workflows, approvals, reports, and platform health
- Contract, security, and compatibility tests

### Excluded

- Public unrestricted API access
- GraphQL as the primary API
- WebSocket without an approved need
- Autonomous C3-C5 command endpoints
- Arbitrary graph traversal or shell execution
- Stable public SDK guarantees before API review

## 33. Assumptions

- Browser UI and enterprise integrations use the same governed backend contracts.
- Early deployments use HTTPS and JSON within private enterprise boundaries.
- Some operations are asynchronous and can wait for human action.
- APIs evolve before a long-term external compatibility commitment is made.

## 35. Acceptance Criteria

This document is ready to enter Review when:

- OpenAPI, representation, error, version, pagination, concurrency, and idempotency standards are agreed.
- Long-running operations and streaming have explicit state and terminal semantics.
- Authentication, scope, policy, approval, and audit behavior cannot differ between UI and direct API use.
- Hidden resources, secrets, unknown outcomes, and partial work fail safely.
- Initial API domains and compatibility obligations are bounded.
- Architecture, security, backend, frontend, integration, operations, and testing reviewers accept the contract.
